## 자체 구현 vs LangChain 도입 — 트레이드오프 정리

먼저 핵심 프레이밍: 이 프로젝트의 자체 코드는 "프레임워크가 없어서 대충 짠 것"이 아니라, **법률 도메인에 특화된 결정들이 코드에 박혀 있는** 구조입니다. LangChain 도입 평가는 "그 도메인 결정들을 프레임워크 추상화로 바꿔 이득인가"의 문제입니다.

### 1. 컴포넌트별 매핑 (현재 → LangChain 대응 → 평가)

| 단계 | 현재 자체 구현 | LangChain 대응 | 교체 시 평가 |
|---|---|---|---|
| **청킹** | [chunker.py](pipelines/src/pipelines/chunk/chunker.py) — **구조 인지**: 법령은 조문 단위(`law-{name}-{조}`), 판례는 판시사항/판결요지 단위로 분리 | `RecursiveCharacterTextSplitter` 등 **문자/토큰 길이 기반** splitter | ⚠️ **손해 가능**. 현재는 "1조=1청크"처럼 법적 의미 경계로 자름. 길이 기반 splitter는 조문을 중간에 끊거나 두 조를 합쳐 인용 정확도를 해칠 수 있음 |
| **임베딩** | [embedder.py](packages/rag/src/rag/embedder.py) — `sentence-transformers` bge-m3 직접, MPS/CPU 자동, `encode_fn` 주입(테스트) | `HuggingFaceEmbeddings` 래퍼 | ≈ **중립**. 거의 동일. 래퍼 한 겹 추가될 뿐 |
| **벡터 검색** | [retriever.py](packages/rag/src/rag/retriever.py) — `chromadb` 직접 query + `is_grounded`(top1 유사도 임계) | `Chroma` VectorStore + `as_retriever` | ≈ **중립~약손해**. 검색은 동일하나 `is_grounded` 같은 **커스텀 근거판정**은 LangChain 리트리버에 자연스럽게 안 들어가 별도 후처리로 남음 |
| **프롬프트** | [prompt.py](packages/rag/src/rag/prompt.py) — 인용규칙·①②③구조·면책을 명시한 한국어 시스템 프롬프트 + 번호 근거 조립 | `ChatPromptTemplate` + `create_stuff_documents_chain` | ≈ **중립**. 템플릿 객체로 옮길 수 있으나 지금도 충분히 단순 |
| **인용 검증** | [citations.py](packages/rag/src/rag/citations.py) — `[n]` 정규식으로 **환각 인용 제거** + Source 매핑 | 표준 대응 **없음** | ❌ **LangChain에 없음**. 자체 유지 필요(LangChain citation 체인들은 포맷이 다름) |
| **오케스트레이션** | [pipeline.py](apps/api/src/api/pipeline.py) `run_chat` — 검색→근거판정→프롬프트→스트림→인용정리→면책 append | `LCEL` 체인 / `RetrievalQA` | ⚖️ **양면**. LCEL로 선언적 표현 가능하나, 현재의 **조건 분기**(근거 부족 시 거절 메시지, 토큰 스트림 중간 가공)는 LCEL에 욱여넣기 까다로움 |
| **LLM 추론** | [llm.py](apps/api/src/api/llm.py) — 자체 `LLM` Protocol + `MlxLLM`(mlx-lm 직접) | `ChatOpenAI` 등. **MLX 1급 통합 없음** | ❌ **MLX는 LangChain 1급 지원 빈약**. 커스텀 LLM 클래스로 감싸야 해서 지금과 작업량 비슷 |

### 2. LangChain 도입이 **실제로 더해줄 것** (pros)

- **생태계 부품**: 다양한 splitter, 리트리버 조합(MMR, multi-query, parent-document, 하이브리드 BM25+벡터), 리랭커 통합을 기성품으로 시도 가능 → 검색 품질 실험이 빨라짐. 특히 메모리에 적힌 **검색 미스 3건(q03/q11/q14)** 같은 문제를 multi-query·하이브리드로 실험할 때 유용.
- **트레이싱/관측성**: LangSmith로 체인 단계별 입출력·지연 추적 → 배포 문서 §5.5 관측성의 일부를 기성품으로.
- **표준화/온보딩**: 신규 개발자가 익숙한 추상화. 다른 LLM·벡터스토어로 교체가 설정 변경 수준.
- **프롬프트/체인 재사용**: 멀티턴, 요약, 라우팅 등 기능 확장 시 바퀴 재발명 감소.

### 3. LangChain 도입의 **비용·리스크** (cons, 이 프로젝트 기준)

- **도메인 청킹 손실 위험**: 가장 큰 리스크. 현재 구조 인지 청킹은 법률 RAG 품질의 핵심인데, 길이 기반 splitter로 갈아끼우면 recall·인용 정확도 회귀 가능. 유지하려면 결국 **커스텀 splitter**를 LangChain 인터페이스로 다시 써야 함 → 이득 상쇄.
- **의존성 비대화**: 현재 런타임은 `chromadb`·`sentence-transformers`·`mlx-lm`·`fastapi`로 가볍다. LangChain은 전이 의존성이 크고 버전 변동이 잦음 → **배포 이미지 비대·버전 충돌·보안 표면 증가**. 배포 문서가 강조한 "가벼운 투명한 의존성" 장점을 깎음.
- **추상화 누수(leaky abstraction)**: `run_chat`의 조건 분기(근거 거절), 토큰 스트림 가공, `strip_invalid_citations`, 결정적 면책 append 같은 **세밀한 제어**는 LCEL/체인 위에서 오히려 더 장황해짐. 지금은 30줄 함수로 읽힘.
- **MLX 1급 미지원**: 어차피 커스텀 LLM 래퍼가 필요 → LangChain의 "교체 용이성" 이점이 이 프로젝트의 핵심 스택(MLX)에선 약함.
- **블랙박스 디버깅**: 평가 하니스(`packages/eval`)가 `run_chat`을 직접 재사용해 "서빙=평가 동일"을 보장 중. 체인으로 감싸면 이 투명한 결합이 한 겹 가려짐.

| 요인 | 자체 구현에 유리 | LangChain에 유리 |
|---|---|---|
| 도메인 특화 청킹/인용 | ✅ 이미 최적화됨 | |

### 5. 권장 — **전면 도입 말고, 선택적 차용**

현 단계(좁은 법률 RAG, MLX, 정식 배포 준비)에서는 **자체 구현 유지가 합리적**입니다. LangChain 전면 도입의 순이득이 작거나 음수일 가능성이 높습니다(도메인 청킹·인용·MLX 때문). 다만 다음은 **부분 차용**을 검토할 만합니다:

1. **검색 품질 실험에 한정해 LangChain Retriever 도입** — multi-query·하이브리드(BM25+벡터)·리랭커로 q03/q11/q14 미스 개선을 *실험*하고, 효과가 확인된 전략만 자체 `Retriever`에 이식. 프로덕션 의존성으로는 넣지 않음.
2. **관측성은 LangChain 대신 배포 문서의 Prometheus/구조적 로깅 경로 유지** — LangSmith는 외부 SaaS라 "private LLM" 취지·데이터 상주와 충돌 가능. 자체 트레이싱이 더 부합.
3. **청킹·인용·면책·근거판정은 자체 유지** — 도메인 자산이므로 프레임워크로 옮기지 않음.

> 한 줄 결론: **"프레임워크가 주는 기성 검색 전략"이 필요해지는 시점**(검색 품질을 본격적으로 끌어올릴 때)에 **리트리버 계층만** 실험적으로 차용하고, 청킹·인용·오케스트레이션·MLX 서빙은 자체 구현으로 두는 하이브리드가 이 프로젝트에 가장 잘 맞습니다.

원하시면 ①LangChain 하이브리드 리트리버로 q03/q11/q14 미스를 실험하는 구체 계획, 또는 ②전면 LangChain 포팅 시의 작업 항목·리스크 산정 중 하나를 더 깊게 풀어드리겠습니다.
