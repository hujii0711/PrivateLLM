## `packages/eval/src/eval/__init__.py` 의 목적

이 파일은 **0바이트(빈 파일)**입니다. 즉 코드는 전혀 없고, **존재 자체**가 목적입니다 — `eval/` 디렉터리를 **파이썬 패키지로 표식**하는 역할을 합니다.

### 왜 필요한가

`__init__.py`가 있어야 파이썬이 `eval/` 폴더를 **import 가능한 패키지**로 인식합니다. 이 파일 덕분에 같은 폴더의 형제 모듈들을 다음처럼 불러올 수 있습니다:

```python
from eval.runner import ...      # runner.py
from eval.answer_metrics import ...
python -m eval.cli --label baseline   # 메모리에 적힌 평가 실행 커맨드
```

만약 이 파일이 없으면 `eval`이 정식 패키지로 잡히지 않아, 위 import·`-m eval.cli` 실행 경로가 깨지거나 불안정해집니다.

### 왜 "비어 있는데도" 두나

| 관점 | 설명 |
|---|---|
| **패키지 표식** | 내용이 없어도 파일이 존재해야 "이 디렉터리는 패키지다"라는 명시적 신호가 됨 |
| **빌드 대상 일치** | [eval/pyproject.toml](packages/eval/pyproject.toml)의 hatchling이 `packages = ["src/eval"]`로 이 디렉터리를 패키지로 빌드 → `__init__.py`가 그 루트 |
| **일관성** | 이 프로젝트의 **모든 워크스페이스 멤버가 동일 패턴** — `rag`·`api`·`pipelines`의 `__init__.py`도 전부 0바이트 빈 파일. eval만 예외가 아님 |

### 빈 파일 vs 내용 채우기

`__init__.py`에 코드를 넣으면 **패키지 import 시 자동 실행**되어, 공개 API를 끌어올리는 용도로 쓸 수 있습니다:

```python
# 예: 이렇게 쓰면 from eval import run_eval 가능 (현재는 안 함)
from .runner import run_eval
```

이 프로젝트는 그렇게 하지 않고 **명시적 전체경로 import**(`from eval.runner import ...`)를 선호합니다. 이 방식의 장점:

- **import 부작용 없음** — 패키지를 불러도 무거운 모듈(예: judge가 끌어오는 LLM)이 줄줄이 로드되지 않음.
- **순환 import 회피** — `__init__`이 비어 있으면 모듈 간 의존 꼬임이 생기기 어려움.
- **명시성** — 어떤 심볼이 어느 모듈에서 오는지 경로에 그대로 드러남.

### 정리

`eval/__init__.py`는 **`eval`을 import 가능한 파이썬 패키지로 만들기 위한 빈 표식 파일**이고, 의도적으로 비워 둬서 import 부작용 없이 `from eval.<module> import ...` / `python -m eval.cli` 경로만 열어 둡니다. 프로젝트의 다른 모든 패키지(`rag`·`api`·`pipelines`)와 똑같은 규칙입니다.

> 참고: `eval/`에는 `__pycache__`(바이트코드 캐시)도 보이는데, 이건 앞서 설명한 자동 생성 캐시라 역할과 무관합니다.
