## `apps/api/src/api/__pycache__/` 의 역할

결론부터: **이 디렉터리는 프로젝트에서 아무 기능적 역할도 하지 않습니다.** CPython이 자동 생성하는 **바이트코드 캐시**일 뿐이고, 언제든 삭제해도 무방합니다(다음 import 시 재생성).

### 각 파일이 무엇인가

`.pyc` 파일은 같은 이름의 `.py` 소스를 **컴파일한 바이트코드 캐시**입니다. `cpython-311`은 이 캐시를 만든 인터프리터가 CPython 3.11(이 프로젝트 `.venv` 버전)임을 뜻합니다.

| 캐시 파일 | 원본 소스 | 원본의 역할 |
|---|---|---|
| `__init__.cpython-311.pyc` | [__init__.py](apps/api/src/api/__init__.py) | `api` 패키지 표식 |
| `llm.cpython-311.pyc` | [llm.py](apps/api/src/api/llm.py) | `LLM` Protocol·`MlxLLM`·`FakeLLM` (추론 백엔드) |
| `main.cpython-311.pyc` | [main.py](apps/api/src/api/main.py) | FastAPI 앱·`/chat`(SSE)·`/health` |
| `pipeline.cpython-311.pyc` | [pipeline.py](apps/api/src/api/pipeline.py) | `run_chat` RAG 오케스트레이션 |
| `schemas.cpython-311.pyc` | [schemas.py](apps/api/src/api/schemas.py) | `ChatRequest`·`SourceOut` (pydantic) |
| `settings.cpython-311.pyc` | [settings.py](apps/api/src/api/settings.py) | `Settings` 구성 |

> `__pycache__` 안에 원본 없는 캐시(예: 별도 `.py`가 사라진 잔여물)는 없습니다 — 6개 캐시 모두 현재 소스 6개와 1:1 대응합니다.

### 동작 방식 (왜 생기나)

1. 파이썬이 모듈을 **처음 import**할 때 `.py`를 파싱→바이트코드로 컴파일하고, 그 결과를 `__pycache__/<모듈>.cpython-311.pyc`에 저장합니다.
2. 다음 import 때는 소스의 수정시각/크기를 캐시 헤더와 비교해, **변경이 없으면 재컴파일을 건너뛰고** `.pyc`를 바로 로드합니다 → 시작 속도 최적화.
3. 소스를 고치면 캐시는 무효화되어 자동 갱신됩니다. 타임스탬프를 보면 `llm.pyc`(6/5 01:27)는 QLoRA 작업 때 `llm.py`를 마지막 수정·실행한 흔적이고, 나머지(6/4 21:08)는 그때 import된 시점입니다.

### 프로젝트 관점에서의 취급

- **버전관리 제외 대상**: 루트 [.gitignore](.gitignore)에 `__pycache__/`가 있어 git에 추적되지 않습니다(레포에 커밋된 적 없음).
- **삭제 안전**: `find . -name __pycache__ -type d -exec rm -rf {} +` 등으로 지워도 기능 영향 없음. 다음 실행 때 다시 생깁니다.
- **배포 영향 없음**: 배포 문서의 컨테이너 이미지는 소스에서 새로 빌드/설치하므로 이 캐시를 옮기지 않습니다. 오히려 호스트의 `cpython-311` 캐시를 이미지에 섞으면 인터프리터 버전 불일치로 무시될 뿐입니다.

즉, **개발 편의를 위한 자동 산출물**이고 프로젝트 로직·배포에는 관여하지 않습니다.
