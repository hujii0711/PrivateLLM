ftdata 6개 파일을 모두 읽었습니다. 동작 방식과 상호관계를 분석합니다.

## 0. 이 패키지가 하는 일 (한 문장)

`ftdata`는 **rejection-sampling distillation**으로 QLoRA 학습 데이터를 만듭니다 — 평가셋과 겹치지 않는 질문 풀에 대해, **서빙과 똑같은 RAG 경로(`run_chat`)로 K개 후보 답변을 생성**하고, **형식·근거 품질로 거르고**, 통과분만 **MLX chat JSONL**(train/valid)로 떨굽니다. 크롤링이 아니라 "자기 모델 출력을 평가지표로 선별"하는 방식입니다.

## 1. 모듈별 책임

| 파일 | 책임 | 핵심 재사용 |
|---|---|---|
| [questions.py](packages/ftdata/src/ftdata/questions.py) | 질문 풀 로더(`question_pool.jsonl`) | — |
| [generate.py](packages/ftdata/src/ftdata/generate.py) | 질문→K후보 생성 + 근거 점수 | `api.pipeline.run_chat`, `eval.judge.groundedness_score` |
| [filter.py](packages/ftdata/src/ftdata/filter.py) | 형식 합격 판정(구조·인용·면책·출처) | `eval.answer_metrics.answer_metrics` |
| [builder.py](packages/ftdata/src/ftdata/builder.py) | 후보→MLX chat 예제 변환 + train/valid 분할 + JSONL 쓰기 | `rag.prompt.build_messages` |
| [cli.py](packages/ftdata/src/ftdata/cli.py) | 전체 오케스트레이션(조립·실행·통계) | `api.llm.MlxLLM`, `api.settings`, `rag.retriever`, + 위 4개 |
| [__init__.py](packages/ftdata/src/ftdata/__init__.py) | 패키지 표식(빈 파일) | — |

## 2. 의존 그래프

```
                         cli.py  ◀── (python -m ftdata.cli)
            ┌──────┬──────┴───────┬────────┐
            ▼      ▼              ▼        ▼
       questions generate      filter   builder
                   │             │         │
        ┌──────────┼──────┐      │         │
        ▼          ▼      ▼      ▼         ▼
   api.pipeline  eval.  rag.   eval.     rag.
   .run_chat     judge  types  answer_   prompt
                              metrics
   + cli가 직접: api.llm.MlxLLM, api.settings.Settings, rag.retriever.Retriever
```

핵심 관찰:
- **cli.py가 조립 지점(composition root)** — `api`·`rag`의 실물(LLM·Settings·Retriever)을 만들고 4개 잎 모듈을 순서대로 호출. apps/api의 main.py와 동일한 패턴.
- **4개 잎 모듈(questions·generate·filter·builder)은 서로를 모릅니다.** 전부 cli가 잇습니다. 순환 의존 없음.
- **ftdata는 `rag`·`api`·`eval` 셋 다에 의존**([pyproject.toml](packages/ftdata/pyproject.toml)의 `dependencies = ["rag","api","eval"]`). 워크스페이스에서 가장 상위 소비자 — 다른 패키지 결과물을 조합하는 "최종 사용자" 위치.

## 3. 데이터 흐름 (한 질문이 학습 예제가 되기까지)

```
question_pool.jsonl
   │ questions.load_questions()
   ▼
질문 q  ────────────────────────────────────────────────┐
   │ generate.generate_candidates(q, retriever, llm, judge_fn, k=6, temp=0.7)
   │   1. hits = retriever.retrieve(q)              # 근거 1회 검색(후보 공유)
   │   2. K번 반복:
   │        events = run_chat(q, retriever, llm, temp=0.7)   # ★서빙과 동일 경로, 온도만 ↑
   │        done   = (type==done 이벤트)
   │        grounded = groundedness_score(q, done.answer, contexts, judge_fn)  # eval.judge
   │   → (hits, [Candidate(answer, sources, grounded) × K])
   ▼
cli 필터링:
   kept = [c for c in cands if filter.format_ok(c.answer, c.sources)   # 구조·[n]·면책·출처
                              and c.grounded >= min_ground]            # 근거 임계
   kept.sort(grounded ↓)[:per_q]                                       # 질문당 상위 per_q
   ▼
builder.to_chat_example(q, hits, c.answer)
   = build_messages(q, hits) + {role:assistant, content:answer}        # ★train입력 = 서빙입력
   ▼  (전체 누적 후)
builder.split_train_valid(examples, valid_every=10)   # 10번째마다 valid (결정적)
   ▼
write_jsonl → data/ft/train.jsonl, valid.jsonl + stats.json
```

## 4. 설계의 핵심 — "재사용으로 일관성 보장"

이 패키지의 정체성은 **학습 데이터 생성 경로를 서빙·평가와 강제로 일치**시키는 것입니다. 세 곳에서 재사용이 일어납니다:

| 재사용 | 위치 | 보장하는 것 |
|---|---|---|
| `api.pipeline.run_chat` | generate.py | **train 후보 생성 = 실제 서빙 경로**(검색·프롬프트·인용정리·면책 동일). 온도만 0.7로 올려 다양성 확보 |
| `rag.prompt.build_messages` | builder.py | **학습 입력(system+user 근거) = 서빙 입력**. 모델이 학습 때 본 포맷 = 추론 때 받는 포맷 |
| `eval.answer_metrics` / `eval.judge` | filter.py / generate.py | **선별 기준 = 평가 기준**. train에 들어갈 답변이 평가셋에서 측정하는 품질지표(구조·인용·면책·groundedness)와 동일 잣대 |

→ 결과: "**train입력 = 서빙입력**, **선별기준 = 평가기준**"이 코드 레벨에서 강제됩니다. (프로젝트 메모리의 "builder=rag.prompt.build_messages 재사용", "filter=eval.answer_metrics 재사용"이 이것)

## 5. rejection-sampling distillation의 구현 디테일

- **다양성**: `run_chat`을 `temperature=0.7`로 K회 호출(서빙은 0.2) → 같은 질문에 다른 후보. 그중 좋은 것만 채택 = "rejection sampling".
- **자기-distillation**: teacher = base Qwen 자신(별도 강한 모델 아님). → 메모리의 A/B 음성 결과 원인 ①"자기-distillation 상한(타깃=base 출력)"이 바로 여기서 비롯.
- **이중 필터**: `format_ok`(형식, AND 4조건) **그리고** `grounded >= min_ground`(내용). 둘 다 통과만 채택.
- **질문당 상한**: `grounded` 내림차순 정렬 후 `per_q`개만 → 특정 질문이 데이터셋을 과점유하지 않게.
- **judge_fn**: `llm.stream(..., max_tokens=16, temperature=0.0)` 람다로 만든 결정적 판정기. groundedness_score가 이 judge_fn으로 LLM-as-judge 채점.
- **결정적 분할**: `(i+1) % 10 == 0`을 valid로 → 시드·랜덤 없이 재현 가능(메모리: train 45/valid 4).

## 6. cli.py의 부수적 패턴 & 개선 여지

- **`_arg` 수동 파서**: `argparse` 대신 `sys.argv.index(name)+1`로 `--k`·`--per-q`·`--min-ground`만 파싱. `type(default)(...)`로 형변환. 가볍지만 **인자 누락/오타 시 에러 처리 빈약**(값 없는 플래그면 IndexError, 미지 플래그는 무시).
- **출력 위치**: `parents[4]`로 레포 루트 역산 → `data/ft/`(gitignore 산출물). questions는 `parents[2]`로 패키지 루트의 `question_pool.jsonl`(버전관리 대상) 참조 — 경로 기준이 둘로 나뉘니 주의.
- **진행 로그**: 질문마다 `[i/N] kept x/y` 출력 + 말미 stats.json(pass_rate 등). 메모리의 "30문항→120후보→49채택(pass_rate 0.41)"이 이 stats.
- **개선 여지**: `_arg` → argparse 전환, generate의 K 루프는 순차(느림) → 병렬화 여지, `judge_fn` 람다가 cli에 묻혀 있어 테스트가 어려움(generate에 주입은 되나 생성은 cli) 정도.

## 7. apps/api와의 구조적 대조

| | apps/api | ftdata |
|---|---|---|
| 조립 지점 | `main.py` (`create_app`) | `cli.py` (`main`) |
| 잎 모듈 결합 | 별 모양, 서로 모름 | 동일(별 모양) |
| 실행 형태 | 상주 서버(SSE) | 1회성 배치 잡 |
| `run_chat` 역할 | 사용자 응답 스트리밍 | 학습 후보 생성(소비자 입장) |
| 외부 의존 | rag만 | rag + **api + eval** (상위 소비자) |

→ 두 패키지가 같은 "조립 지점이 잎 모듈을 잇는다" 패턴을 공유하고, ftdata는 그 위에서 api·eval을 **재사용**해 "서빙=학습=평가 일치"를 만든 것이 핵심입니다.
