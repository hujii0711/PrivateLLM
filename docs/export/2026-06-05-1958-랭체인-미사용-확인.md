## 아니요, 랭체인(LangChain)을 전혀 사용하지 않았습니다

세 가지 레벨에서 모두 확인했습니다 — 흔적이 없습니다:

| 확인 대상 | 결과 |
|---|---|
| 소스 코드 `import` (`packages`·`apps`·`pipelines`) | LangChain / LlamaIndex / Haystack import **0건** |
| `pyproject.toml` 의존성 선언 | langchain 계열 **선언 없음** |
| `.venv` 실제 설치 (전이 의존성 포함) | `import langchain` 실패, site-packages에 **없음** |

## 대신 무엇을 직접 썼나

이 프로젝트는 RAG 프레임워크 없이 **저수준 라이브러리를 직접 조합**한 구조입니다:

| 기능 | 사용 라이브러리 | 위치 |
|---|---|---|
| 청킹 | 자체 구현 | [pipelines/.../chunk/chunker.py](pipelines/src/pipelines/chunk/chunker.py) |
| 임베딩 | `sentence-transformers` (bge-m3) 직접 호출 | [rag/embedder.py](packages/rag/src/rag/embedder.py) |
| 벡터 검색 | `chromadb` 클라이언트 직접 호출 | [rag/retriever.py](packages/rag/src/rag/retriever.py) |
| 프롬프트 구성 | 자체 `build_messages` | [rag/prompt.py](packages/rag/src/rag/prompt.py) |
| 인용/근거 정리 | 자체 구현 | [rag/citations.py](packages/rag/src/rag/citations.py) |
| 오케스트레이션 | 자체 `run_chat` (검색→근거판정→프롬프트→스트림→인용) | [api/pipeline.py](apps/api/src/api/pipeline.py) |
| LLM 추론 | `mlx-lm` 직접 호출 | [api/llm.py](apps/api/src/api/llm.py) |

즉 LangChain의 `Chain`/`Retriever`/`TextSplitter` 추상화 대신, **각 단계를 직접 작성**해 RAG 파이프라인을 구성했습니다.

### 이 선택의 함의 (배포 관점)

- **장점**: 의존성이 가볍고(추상화 레이어·전이 의존성 없음) 동작이 투명함 → 배포 이미지가 작고, 버전 충돌·블랙박스 디버깅 리스크가 적습니다. 배포 문서의 `OpenAICompatLLM` 스왑([02 Linux GPU](docs/superpowers/release/02-linux-gpu.md))이 쉬운 것도 자체 `LLM` Protocol을 직접 정의했기 때문입니다.
- **유의점**: 프레임워크가 주는 기성 기능(다양한 splitter, 리트리버 조합, 트레이싱 통합 등)은 필요 시 직접 구현해야 합니다. 다만 현재 도메인(법령·판례 RAG)은 범위가 좁아 직접 구현이 오히려 단순합니다.

원하시면 이 자체 구현 방식과 LangChain 도입 시의 트레이드오프를 더 정리해 드리겠습니다.
