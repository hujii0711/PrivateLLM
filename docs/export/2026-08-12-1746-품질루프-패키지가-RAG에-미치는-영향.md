## 한 줄 요약

세 패키지는 **RAG 런타임 경로에 들어가지 않습니다.** `POST /chat` 요청은 `retriever → build_messages → llm.stream` 만 지나가고 eval/ftdata/finetune 코드는 한 줄도 실행되지 않습니다. 이들은 RAG 시스템 **바깥에서 도는 품질 루프**이고, 실제 런타임에 영향을 주는 접점은 **딱 하나 — 생성 LLM에 LoRA 어댑터를 갈아끼우는 것**입니다.

의존 방향도 그걸 뒷받침합니다: `rag ← api ← eval ← ftdata` 단방향이라, RAG 쪽은 이 세 패키지의 존재를 모릅니다.

---

## 각 패키지가 RAG에 대해 하는 일

### packages/eval — RAG를 **측정**한다 (변경하지 않음)

[runner.py:88-115](../../packages/eval/src/eval/runner.py#L88-L115)가 평가 항목 1건마다 실서빙과 **동일한** `run_chat()`을 호출합니다. 별도 평가용 경로를 만들지 않았다는 게 핵심 — 평가한 것이 곧 서빙되는 것입니다.

측정 축이 두 갈래로 나뉩니다:

| 축 | 지표 | 무엇을 잡아내나 |
|---|---|---|
| 검색 | `recall_at_k` ([retrieval_metrics.py](../../packages/eval/src/eval/retrieval_metrics.py)) | 청킹·임베딩·top_k 설정 문제 |
| 생성 | `citation_rate`, `structure_rate`, `disclaimer_rate`, `sources_rate`, `mention_coverage`, `groundedness` | 프롬프트·모델 문제 |

이 분리가 RAG 운영에서 가장 실용적인 부분입니다. 답변이 나빠졌을 때 **"검색이 못 찾은 건지, 모델이 못 쓴 건지"** 를 숫자로 가릅니다. `recall_at_k`가 낮으면 파인튜닝은 헛수고고 `pipelines/chunk`·`index`를 손봐야 합니다.

### packages/ftdata — RAG를 **자기 자신의 교사로** 쓴다

[ftdata/cli.py](../../packages/ftdata/src/ftdata/cli.py)의 흐름: 질문 풀 → 같은 `run_chat()`을 `temperature=0.7`로 k회 호출해 후보 생성 → 형식·근거 필터 → 상위 `per_q`개 채택 → MLX chat JSONL.

RAG 관점에서 두 가지가 중요합니다:

1. **[builder.py:40-44](../../packages/ftdata/src/ftdata/builder.py#L40-L44)** — 학습 예제의 system/user 메시지를 서빙과 **똑같은 `build_messages()`** 로 만듭니다. 즉 모델은 "검색 근거가 붙은 그 프롬프트 형태에서 어떻게 답해야 하는가"를 학습합니다. RAG 프롬프트 구조에 특화된 학습입니다.
2. **[filter.py](../../packages/ftdata/src/ftdata/filter.py)** — 채택 기준이 `eval.answer_metrics`를 그대로 재사용합니다. 평가 잣대와 학습 잣대를 일부러 일치시킨 설계입니다.

이것은 외부 정답 데이터 없이 **자기 출력 중 좋은 것만 골라 다시 학습하는 self-distillation(거부 샘플링)** 구조입니다.

### packages/finetune — 학습 명령을 조립하고 **개선 여부를 판정**한다

[train.py](../../packages/finetune/src/finetune/train.py)는 `mlx_lm.lora` 명령어 리스트를 만드는 순수 함수일 뿐이고, [compare.py](../../packages/finetune/src/finetune/compare.py)가 `baseline.json` vs `qlora.json`의 지표별 Δ를 계산합니다.

여기서 RAG에 가해지는 **유일한 실제 변경**이 나옵니다 — `data/adapters/qlora` 어댑터. `MlxLLM(model, adapter_path=...)` ([llm.py:131](../../apps/api/src/api/llm.py#L131))로 로드하면 RAG 파이프라인의 생성 단계가 바뀝니다. 검색·프롬프트·인용 검증은 그대로입니다.

## 루프 전체

```
RAG 서빙 ──run_chat──> eval (측정) ──기준 재사용──> ftdata (데이터)
    ↑                                                    │
    └────────── 어댑터 교체 ── finetune (학습+A/B) ←──────┘
```

`run_chat`이 허브고, 세 패키지 모두 이 함수 하나를 공유합니다.

## 실제로 RAG에 미치는 영향의 한계 — 확인된 사항

이 구조를 그대로 돌렸을 때 기대할 수 있는 것과 없는 것이 명확히 갈립니다.

**1. 파인튜닝은 검색 품질을 절대 못 올립니다.** `run_item`은 어댑터와 무관한 동일 `Retriever`를 쓰므로, `recall_at_k`는 baseline과 qlora가 **정의상 같은 값**이 나옵니다. compare 표에 `recall_at_k` Δ가 항상 `+0.000`으로 찍히는 건 버그가 아니라 당연한 결과입니다. 검색 개선은 `pipelines` 쪽 일입니다.

**2. `disclaimer_rate`도 개선 여지가 없습니다.** [pipeline.py:157](../../apps/api/src/api/pipeline.py#L157)의 `_ensure_disclaimer()`가 면책 문구를 무조건 덧붙이므로 baseline에서 이미 1.0입니다. 마찬가지로 `strip_invalid_citations`가 잘못된 인용을 후처리로 제거하므로, 형식 지표 상당수는 **모델이 아니라 파이프라인이 보장**하고 있습니다.

→ 결국 파인튜닝이 실제로 움직일 수 있는 지표는 `structure_rate`, `mention_coverage`, `groundedness` 정도입니다.

**3. 학습 잣대 = 평가 잣대라 지표가 오르는 게 당연합니다.** ftdata가 `answer_metrics`와 `groundedness_score`로 후보를 거르고, eval이 **같은 함수로** 채점합니다. 같은 자로 훈련해서 같은 자로 재는 구조라 Δ가 양수인 건 품질 향상의 증거가 아닐 수 있습니다. 다만 질문 풀은 평가셋과 disjoint하게 분리해 뒀으므로([questions.py](../../packages/ftdata/src/ftdata/questions.py)) 질문 누수는 막혀 있습니다.

**4. judge 편향 — eval은 막았고 ftdata는 안 막았습니다.** [eval/cli.py:92](../../packages/eval/src/eval/cli.py#L92)는 judge를 항상 어댑터 없는 base 모델로 고정해 공정성을 지킵니다. 반면 [ftdata/cli.py:114](../../packages/ftdata/src/ftdata/cli.py#L114)의 `judge_fn`은 후보를 만든 그 `llm`을 그대로 씁니다 — 자기 답변을 자기가 채점해 학습 데이터를 고릅니다.

**5. 학습된 어댑터가 서빙에 연결되어 있지 않습니다.** [main.py:171](../../apps/api/src/api/main.py#L171)은 `MlxLLM(settings.mlx_model)`만 호출하고, [settings.py](../../apps/api/src/api/settings.py)에는 `adapter_path` 필드 자체가 없습니다. A/B에서 어댑터가 좋다고 판정되어도 **현재 코드로는 `/chat`에 반영할 방법이 없습니다.** 아키텍처 문서의 `FT -.->|어댑터 교체| LLM` 화살표는 아직 미구현 상태입니다. 이걸 잇는 게 루프를 닫는 데 필요한 최소 작업입니다.
