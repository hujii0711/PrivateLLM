pipelines의 17개 파일을 모두 읽었습니다. 이 패키지는 **Plan 1 = 데이터 수집·색인 파이프라인(write path)**으로, `rag`가 런타임에 읽는 Chroma 인덱스를 **생성**하는 쪽입니다. 동작 방식과 상호관계를 분석합니다.

## 0. 정체성 — 전형적 ETL, 파일 산출물로 연결

```
Extract(ingest)  →  Transform(clean+chunk)  →  Load(index)
법령/판례 API        정규화 + 구조 청킹           bge-m3 임베딩 + Chroma
   ↓ data/raw/*.json    ↓ data/chunks/chunks.jsonl   ↓ data/chroma/
```

**단일 오케스트레이터가 없습니다.** 세 단계가 각각 독립 `python -m` 진입점이고, **단계 간 연결은 함수 호출이 아니라 `data/` 디렉터리의 파일**입니다(raw JSON → chunks JSONL → Chroma). 이게 이 패키지를 이해하는 핵심 멘탈모델입니다.

## 2. 의존 그래프 (패키지 내부)

```
       fetch_corpus.main ──▶ law_client ─(http)─ DRF API
        (ingest)        ├──▶ law_parser  (XML→dict)
                        ├──▶ prec_parser (XML→dict)
                        └──▶ config

       chunker.main ────────▶ clean.normalize   ← 유일한 cross-subpackage 의존
        (chunk)      ────────▶ schema.make_chunk
                     ────────▶ config

       build_index.main ────▶ index.embedder ─(lazy)─ sentence-transformers
        (index)       ───────▶ chromadb
                      ───────▶ config

       cli/query.main ──────▶ index.embedder, index.build_index.COLLECTION
```

핵심 관찰:
- **세 진입점은 서로를 import하지 않습니다.** 오직 파일(raw→chunks→chroma)로 이어집니다 → 단계별 독립 실행·재실행 가능.
- **`config`·`schema`가 공통 척추(spine)** — 모든 단계가 config로 경로를, chunk가 schema로 타입을 공유.
- **cross-subpackage 의존은 단 하나**: `chunk/chunker` → `clean/normalize`. 나머지는 각자 루트(config/schema)나 외부 라이브러리만 봄 → 응집도 높고 결합도 낮음.
- **`pipelines`는 `rag`·`api`·`eval`을 import하지 않습니다.** 의존성은 `requests`·`lxml`·`chromadb`·`sentence-transformers`뿐. 즉 **완전히 독립**이고, rag와는 "코드 의존"이 아니라 "**산출물(Chroma) 공유**"로만 연결됩니다.

## 3. 단계별 동작 디테일

### ① Extract — `fetch_corpus.collect` ([fetch_corpus.py](pipelines/src/pipelines/ingest/fetch_corpus.py))
- 법령(`주택임대차보호법`,`민법`)·판례(보증금 반환 관련 3쿼리) 수집.
- **견고성 처리 두 가지**:
  - `_match_law_mst`: 검색이 가나다순이라 "민법" 검색 시 "**난민법**"이 먼저 나오는 문제 → **법령명 정확 일치** 항목을 골라 엉뚱한 법령 수집 방지(없으면 첫 결과 폴백).
  - 판례: `seen` set으로 **중복 제거**, `<PrecService>` 없는 빈 본문·`case_no` 없는 결과 스킵.
- `law_client`(HTTP) → `law_parser`/`prec_parser`(파싱) → `_write`(raw JSON). `source_url`·`prec_id` 부착.

### ② Transform — `chunker.build_all` ([chunker.py](pipelines/src/pipelines/chunk/chunker.py))
- **구조 인지 청킹**(길이 기반 아님): 법령은 **조문 1개 = 청크 1개**(`law-{법}-{조}`), 판례는 **판시사항/판결요지 각각 청크**(`prec-{id}-{판시사항|판결요지}`).
- 각 청크 본문은 `clean.normalize`로 정규화, `schema.make_chunk`로 **source_type 검증**(`법령/판례/해설/상담사례`만 허용) 후 생성.
- ⚠️ `해설`·`상담사례`는 스키마에만 있고 현재 수집 안 함(메모리의 "3B에서 채울 여지").

### ③ Load — `build_index.build_index` ([build_index.py](pipelines/src/pipelines/index/build_index.py))
- chunks.jsonl 로드 → 64개씩 배치 → `embedder.embed`(bge-m3, **normalize=True**) → Chroma `upsert`.
- 컬렉션 `jeonse_deposit`, **`hnsw:space=cosine`**. 메타데이터(source_type/title/ref/url/date)도 함께 저장 → rag가 검색 시 그대로 꺼냄.
- `upsert`라 **재실행 시 id 기준 갱신**(멱등) → 블루/그린 재색인의 기반.

## 4. 이 프로젝트 전체와의 연결점 (중요)

### (A) rag와의 "암묵적 계약"
pipelines와 rag는 import로 안 엮였지만, **세 상수가 양쪽에서 일치해야** 동작합니다:

| 계약 | pipelines(write) | rag(read) |
|---|---|---|
| 컬렉션명 | `build_index.COLLECTION="jeonse_deposit"` | `rag/config.COLLECTION` |
| 임베딩 모델 | `index/embedder.MODEL_NAME="BAAI/bge-m3"` | `rag/config.MODEL_NAME` |
| 거리척도 | `hnsw:space=cosine` + `normalize_embeddings=True` | retriever가 `1.0 - distance`로 유사도 환산 |

→ **이 상수들이 중복 정의**돼 있고 둘이 어긋나면 검색이 조용히 붕괴합니다(메모리의 비자명 인계사항). 배포 시 재색인의 **평가 회귀 게이트**가 이 불일치를 잡는 안전장치입니다.

### (B) 챗봇이 인용하는 "제3조의2"의 출처
[law_parser.py](pipelines/src/pipelines/ingest/law_parser.py)의 `_normalize_no(no, branch)`가 **가지조문**(`조문가지번호`)을 `제3조의2` 형태로 만듭니다. 챗봇이 보증금 우선변제로 늘 인용하는 그 조문이 바로 여기서 정규화돼 청크의 `ref`가 됩니다 — 파서의 작은 분기가 최종 답변 인용까지 이어지는 셈.

## 5. 공통 설계 패턴 & 개선 여지

**패턴**:
- **`encode_fn`/`session` 주입**: embedder·LawClient가 외부 의존을 주입받아 **테스트 가능**(실 모델·네트워크 없이). rag/api와 동일 철학.
- **지연 import**: embedder가 `sentence_transformers`·`torch`를 메서드 안에서 로드 → 무거운 의존을 실제 임베딩 때만.
- **TypedDict + 검증 팩토리**: `make_chunk`가 잘못된 source_type을 생성 시점에 차단.
- **파일 기반 단계 분리**: 각 단계 독립 재실행, 중간 산출물 검수 용이.

**개선 여지**:
- **상수 중복**(COLLECTION/MODEL_NAME이 pipelines·rag 양쪽) → 공유 모듈로 단일화하면 (A)의 드리프트 리스크 제거.
- **오케스트레이션 부재**: 세 `main`을 수동 순차 실행 → 재색인 운영 잡(make 타깃/단일 CLI)으로 묶으면 배포 문서의 재색인 파이프라인이 깔끔.
- **`index/embedder`와 `rag/embedder`가 거의 동일 코드**(중복) → 공유 가능하나, 패키지 독립성과의 트레이드오프.
- `해설`/`상담사례` 미수집 → RAG 코퍼스·검색 미스(q03/q11/q14) 보강 여지.

## 6. 세 패키지 구조 대조 (apps/api · ftdata · pipelines)

| | apps/api | ftdata | pipelines |
|---|---|---|---|
| 성격 | 상주 서버(read) | 배치(학습데이터) | 배치(ETL, write) |
| 조립 지점 | main.py | cli.py | **없음**(3개 main, 파일로 연결) |
| 외부 워크스페이스 의존 | rag | rag+api+eval | **없음**(독립) |
| 산출물/역할 | SSE 응답 | train/valid JSONL | **Chroma 인덱스(모두의 토대)** |

→ pipelines는 의존이 가장 적은 **최하부 토대**이고, 나머지가 그 산출물(Chroma) 위에서 동작합니다. "코드는 독립, 데이터로 연결"이 이 패키지의 핵심 성격입니다.
