`packages/rag`는 보증금 챗봇의 **RAG 코어 라이브러리**입니다. 앞서 본 eval·finetune이 "측정·학습"이었다면, rag는 챗봇의 **실제 검색·근거·인용 로직** 그 자체입니다. 6개 파일(+빈 `__init__.py`)이 명확한 단방향 의존으로 쌓여 있습니다. 단, rag 자신은 **오케스트레이션을 하지 않습니다** — 부품만 제공하고, 조립은 `api.pipeline.run_chat`이 합니다.

## 의존 그래프 (단방향, 순환 없음)

```
                    types.py  (Retrieved, Source — 공용 데이터 모델, 의존 0)
                   ╱    │    ╲
          config.py  embedder  prompt.py   citations.py
              │      .py │         (types)     (types)
              │         │
              └──► retriever.py ◄── embedder, config, types
                       │
                       ▼  (외부: chromadb)
              ───────────────────────────────
              api.pipeline.run_chat (오케스트레이터, rag 밖)
              검색→근거판정→프롬프트→생성→인용정리
```

핵심: **types.py가 모든 것의 바닥**이고, retriever만 다른 rag 모듈을 끌어모읍니다. prompt·citations는 서로 모르고 types만 압니다.

## 파일별 역할

**1. [types.py](packages/rag/src/rag/types.py) — 공용 데이터 모델 (의존 0)**
- `Retrieved`: 검색 결과 한 건(text, `similarity`=1−distance, 메타데이터 ref/title/url/date 등).
- `Source`: 답변에 실제 인용된 근거(`n`=인용번호 [n] + 출처 메타).
- 두 dataclass가 패키지 전체의 공용어. retriever가 `Retrieved`를 만들고, citations가 그것을 `Source`로 변환합니다.

**2. [config.py](packages/rag/src/rag/config.py) — 설정 + 상수**
- `RagConfig` dataclass: chroma 경로, 컬렉션명, 모델명, `top_k=6`, `min_similarity=0.35`.
- **Plan 1 색인과 반드시 일치해야 하는 값**(`COLLECTION="jeonse_deposit"`, `MODEL_NAME="BAAI/bge-m3"`)을 모듈 상수로 고정 — 질의 임베딩과 색인 임베딩이 같은 공간에 있어야 검색이 동작하므로.
- `from_env()`로 `CHROMA_DIR` 환경변수 오버라이드 지원.

**3. [embedder.py](packages/rag/src/rag/embedder.py) — 질의 임베더**
- `QueryEmbedder`가 질문을 bge-m3(1024-dim, normalize)로 벡터화. 색인과 **동일 모델**이 핵심.
- 두 가지 설계 포인트: ① `encode_fn` **주입**으로 테스트 시 진짜 모델 없이 가짜 벡터 사용 가능. ② `_lazy()`로 SentenceTransformer를 첫 호출에야 로드(MPS/CPU 자동 선택) — import 비용 회피.

**4. [retriever.py](packages/rag/src/rag/retriever.py) — 검색 + 근거 판정 (rag의 중심)**
- 유일하게 다른 rag 모듈 3개(config·embedder·types)와 외부 chromadb를 묶는 모듈.
- `retrieve()`: 질의 임베딩 → Chroma `top_k` 검색 → distance를 cosine 유사도로 변환해 `Retrieved` 리스트 생성(메타데이터를 안전하게 `.get()`으로 매핑).
- `is_grounded()`: **최상위 결과의 유사도가 `min_similarity` 미만이면 "근거 부족"** 판정. 이 한 줄이 환각 방지의 1차 게이트입니다.

**5. [prompt.py](packages/rag/src/rag/prompt.py) — 프롬프트 조립**
- `build_messages()`: 검색 결과를 `[1] (제목) 본문` 형태로 번호 매겨 system+user 메시지 생성.
- `SYSTEM_PROMPT`에 **인용 규칙이 강하게 인코딩**돼 있습니다: ①②③ 상담 구조, 모든 사실 문장 끝에 `[n]` 필수, 근거 없는 진술 금지, 마지막 줄 면책문구 고정. eval의 `answer_metrics`가 검사하는 항목들(structure/citation/disclaimer)이 바로 여기서 요구됩니다.

**6. [citations.py](packages/rag/src/rag/citations.py) — 인용 검증·환각 제거 (후처리)**
- `extract_sources()`: 답변의 `[n]`을 스캔해 **유효 범위(1~len(hits)) 안의 것만** 등장 순서·중복 제거로 `Source`로 매핑.
- `strip_invalid_citations()`: 범위를 벗어난 `[n]`(모델이 지어낸 환각 인용)을 텍스트에서 제거.
- 즉 프롬프트로 "인용해라" 요구하고(사전), citations로 "거짓 인용은 지운다"(사후)는 양방향 방어.

## 전체 동작 흐름 (api.pipeline.run_chat이 조립)

rag는 부품 제공자이고, 실제 순서는 [pipeline.py](apps/api/src/api/pipeline.py)가 지휘합니다:

```
query
  │
  ▼ retriever.retrieve(query)           [rag.retriever]
hits: list[Retrieved]
  │
  ▼ retriever.is_grounded(hits)?        [rag.retriever] — 유사도 게이트
  ├─ No  → NO_GROUNDING_MSG 반환(생성 안 함)
  └─ Yes ↓
  ▼ build_messages(query, hits)         [rag.prompt]
messages
  │
  ▼ llm.stream(...)  → 토큰 스트리밍     [api.llm, rag 밖]
raw answer
  │
  ▼ strip_invalid_citations(raw, hits)  [rag.citations] — 환각 인용 제거
  ▼ _ensure_disclaimer(...)             [api.pipeline]   — 면책문구 보강
  ▼ extract_sources(answer, hits)       [rag.citations] — 유효 인용 → Source
  │
  ▼ {"type":"done", answer, sources}
```

rag 6개 모듈 중 **4개(retriever·prompt·citations + types/config)가 이 한 흐름에서 순차 호출**됩니다. embedder는 retriever 내부에 숨겨져 직접 노출되지 않습니다.

## 설계 패턴 요약

eval·finetune과 같은 철학이 일관됩니다: **순수·테스트 가능한 부품 + 외부 의존의 주입/격리**. 구체적으로 —
- **데이터 모델을 바닥에 고정**(types) → 순환 의존 차단.
- **무거운 의존(SentenceTransformer)은 lazy + encode_fn 주입**으로 테스트 격리(embedder).
- **환각 방지를 3중으로 분산**: 검색 유사도 게이트(retriever) → 프롬프트 인용 강제(prompt) → 사후 인용 검증(citations).
- **오케스트레이션은 rag 밖**(api.pipeline)에 둬서, rag는 라이브러리로만 남고 eval도 같은 `retrieve`/`run_chat`을 재사용합니다.
