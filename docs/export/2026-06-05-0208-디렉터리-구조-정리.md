# privateLLM 디렉터리 구조 정리

**주택임대차 보증금 반환 상담 챗봇 PoC** — 로컬 LLM(Qwen2.5-7B / MLX) + RAG. uv 모노레포(워크스페이스)로 구성되어 있고, 데이터 파이프라인 → RAG 백엔드 → 웹 UI → 평가/파인튜닝까지 단계별로 분리되어 있습니다.

## 최상위 구조

```
privateLLM/
├── pyproject.toml      # uv 워크스페이스 루트 (members: pipelines, packages/*, apps/*  /  exclude: apps/web)
├── uv.lock             # 단일 루트 락파일 (모든 Python 멤버 공유)
├── pipelines/          # ① 데이터 파이프라인 (법령·판례 수집 → 청크 → Chroma 인덱싱)
├── packages/           # ② 재사용 Python 라이브러리 (rag / eval / ftdata / finetune)
├── apps/               # ③ 실행 애플리케이션 (api 백엔드 + web 프론트)
├── data/               # ④ 모든 산출물·아티팩트 (gitignore — 재생성 가능)
├── docs/               # ⑤ 설계·계획·실험노트·export
└── .venv/              # 워크스페이스 공용 가상환경
```

> **워크스페이스 핵심**: `apps/web`만 워크스페이스에서 **제외**됩니다(Node/npm 프로젝트라서). 나머지 Python 멤버는 루트 `uv.lock` 하나를 공유합니다.

---

## ① `pipelines/` — 데이터 파이프라인 (Plan 1)

원천 데이터를 수집·정제·청크화하여 Chroma 벡터DB에 인덱싱하는 ETL 단계. `src/pipelines/` 아래 처리 순서대로 모듈이 나뉩니다:

| 모듈 | 역할 |
|------|------|
| `ingest/law_client.py` | 국가법령정보 OpenAPI 호출 (OC키=`fujii0711`, `.env`의 `LAW_API_OC`) |
| `ingest/law_parser.py` · `prec_parser.py` | 법령(조문)·판례 응답 파싱 |
| `ingest/fetch_corpus.py` | 수집 오케스트레이션 → `data/raw/` 저장 |
| `clean/normalize.py` | 텍스트 정규화 |
| `chunk/chunker.py` | 조문/판례 단위 청크 분할 |
| `index/embedder.py` | bge-m3(1024-dim) 임베딩 |
| `index/build_index.py` | Chroma `jeonse_deposit` 컬렉션 빌드 |
| `cli/query.py` | 인덱스 검색 확인용 CLI |
| `config.py` · `schema.py` | 상수·데이터 스키마 |

산출물: 법령 2건 + 판례 24건 → **1264 청크** → `data/chroma`.
⚠️ 임베딩 모델 상수(`COLLECTION`/`MODEL_NAME`)는 여기와 `rag/config.py`에 **중복 정의**되어 있어 항상 일치해야 합니다(인덱싱=질의 동일 임베딩 필수).

## ② `packages/` — 재사용 라이브러리

서빙과 평가가 같은 코드를 공유하도록 핵심 로직을 라이브러리로 분리한 영역입니다.

### `packages/rag/` — RAG 코어 (Plan 2A)
챗봇의 두뇌. `apps/api`가 import해서 사용.
- `embedder.py` / `retriever.py` — 질의 임베딩 + Chroma 검색
- `prompt.py` — 컨텍스트 주입 프롬프트(`build_messages`, 서빙·학습 입력 공통)
- `citations.py` — `[n]` 인용·출처 처리
- `config.py` / `types.py` — 상수·타입

### `packages/eval/` — 평가 하니스 (Plan 3A)
- `runner.py` — `api.pipeline.run_chat` **재사용**(서빙=평가 동일 경로)
- `retrieval_metrics.py`(recall@k) / `answer_metrics.py`(인용·구조·면책률) / `judge.py`(LLM 채점)
- `dataset.py` + `eval_set.jsonl`(16문항, **held-out**) / `report.py` / `cli.py`
- 실행: `uv run --package eval python -m eval.cli --label baseline`

### `packages/ftdata/` — 파인튜닝 데이터 빌더 (Plan 3B)
- **rejection-sampling distillation**(크롤링 아님): 질문→`run_chat` K후보→형식지표 필터→MLX chat JSONL
- `filter.py`(=eval 지표 재사용) / `builder.py`(=rag.prompt 재사용) / `questions.py` + `question_pool.jsonl`(30문항, **평가셋과 disjoint** — 오염 금지)

### `packages/finetune/` — QLoRA 학습 + A/B (Plan 3C)
- `train.py` — `mlx_lm.lora` 커맨드 빌더
- `compare.py` / `compare_cli.py` — baseline vs qlora 델타 비교

## ③ `apps/` — 실행 애플리케이션

### `apps/api/` — FastAPI 백엔드 (Python 워크스페이스 멤버)
| 파일 | 역할 |
|------|------|
| `main.py` | FastAPI 앱, `/health` · `/chat`(SSE) 엔드포인트 |

| `schemas.py` | `ChatRequest{message}` / `SourceOut` |
| `settings.py` | 설정(temperature 등) |

### `apps/web/` — Next.js 16 프론트 (워크스페이스 제외, npm 독립)
- `lib/sse.ts`(SSE 파서) · `chatClient.ts`(fetch+ReadableStream) · `types.ts`
- `hooks/useChat.ts` — 채팅 상태/스트리밍
- `components/` — `Chat` · `MessageBubble` · `ChatInput` · `SourceCard`
- `app/` — App Router(`page.tsx`/`layout.tsx`/`globals.css`)
- `.env.local` — `NEXT_PUBLIC_API_BASE=http://localhost:8000`
- 각 모듈마다 `.test.ts(x)` 동거(Vitest)

## 평가 하니스란
Optimized tool selection**평가 하니스(Evaluation Harness)**는 소프트웨어나 머신러닝 모델의 성능을 체계적으로 측정하고 평가하기 위한 프레임워크/도구 모음입니다. 하네스 엔지니어링과는 완전히 다른 개념입니다.


#### 1. 핵심 개념

**평가 하니스의 역할:**
- 🧪 **자동화된 테스팅**: 다양한 입력/데이터셋에 대해 모델을 일관되게 테스트
- 📊 **메트릭 수집**: 정확도, F1 스코어, BLEU 등 다양한 성능 지표 계산
- 📈 **성능 추적**: 다양한 버전/설정의 모델 간 비교
- 📝 **결과 분석**: 평가 결과를 구조화된 형식으로 저장 및 분석

#### 2. 실제 예시 (당신의 프로젝트에서)

워크스페이스를 보면:
```
packages/eval/              # 평가 하니스 패키지
data/eval_runs/
  ├── baseline.json         # 기본 모델 평가 결과
  └── qlora.json           # LoRA 미세조정 모델 평가 결과
```

이것이 정확히 평가 하니스의 예시입니다. 두 모델의 성능을 같은 기준으로 평가하고 결과를 비교하는 것입니다.

#### 3. 간단한 유추

**하네스(Harness)의 비유**: 말을 통제하기 위한 마구(harness)처럼, 평가 하니스는 모델의 동작을 일관된 방식으로 "통제"하고 측정합니다.
