현재 `pipelines/.env`는 아직 없습니다 (`.env.example`만 존재). 먼저 만들어야 합니다:

```powershell
Copy-Item pipelines\.env.example pipelines\.env
```

`.env`는 [.gitignore:7](.gitignore#L7)로 제외되어 있어 커밋되지 않습니다.

방법은 두 가지이고, 성격이 다릅니다.

---

## 방법 1 — uv의 `--env-file` (코드 변경 0줄)

uv 0.12.3에 이미 내장된 기능입니다:

```powershell
uv run --env-file pipelines\.env pipelines-ingest
```

매번 타이핑하기 싫으면 `UV_ENV_FILE` 환경변수로 고정할 수 있습니다:

```powershell
$env:UV_ENV_FILE = "pipelines\.env"
uv run pipelines-ingest      # 이제 자동 적용
```

**장점:** 코드도, 의존성도 건드리지 않습니다.
**한계:** `uv run`을 거칠 때만 동작합니다. venv를 활성화하고 `pipelines-ingest`를 직접 치면 적용되지 않습니다. 질문하신 "모듈 안에서 적용"은 아닙니다.

---

## 방법 2 — 모듈 안에서 로드 (권장)

**① 의존성 추가** — [pipelines/pyproject.toml](pipelines/pyproject.toml):

```toml
dependencies = [
    "requests>=2.31",
    "lxml>=5.0",
    "chromadb>=0.5",
    "sentence-transformers>=3.0",
    "python-dotenv>=1.0",
]
```

**② 로더 함수 추가** — [pipelines/src/pipelines/config.py](pipelines/src/pipelines/config.py)의 `REPO_ROOT` 근처:

```python
PKG_ROOT = Path(__file__).resolve().parents[2]   # → C:\PrivateLLM\pipelines
DEFAULT_ENV_FILE = PKG_ROOT / ".env"


def load_env_file(path: Path | None = None) -> None:
    """CLI 진입점에서 .env를 프로세스 환경변수로 읽어들인다.

    override=False라서 이미 설정된 실제 환경변수가 .env보다 우선한다.
    CI나 배포 환경이 주입한 값을 파일이 덮어쓰지 않게 하기 위함이다.
    경로는 현재 작업 디렉터리가 아니라 패키지 위치를 기준으로 잡으므로,
    어느 디렉터리에서 실행하든 같은 .env를 읽는다.
    """
    from dotenv import load_dotenv

    load_dotenv(path or DEFAULT_ENV_FILE, override=False)
```

`cwd`가 아니라 `PKG_ROOT` 기준인 점이 중요합니다. 콘솔 스크립트는 아무 디렉터리에서나 실행될 수 있어서, `cwd` 기준으로 찾으면 조용히 실패합니다.

**③ 각 `main()` 첫 줄에서 호출** — [fetch_corpus.py:175](pipelines/src/pipelines/ingest/fetch_corpus.py#L175), [chunker.py:135](pipelines/src/pipelines/chunk/chunker.py#L135), [build_index.py:113](pipelines/src/pipelines/index/build_index.py#L113), [query.py:43](pipelines/src/pipelines/cli/query.py#L43):

```python
def main() -> None:
    from ..config import Config, load_env_file

    load_env_file()
    cfg = Config.from_env()
    ...
```

**④ 재설치:**
```powershell
uv sync
uv run pipelines-ingest      # 이제 .env 자동 적용
```

## ⚠️ `Config.from_env()` 안에 넣으면 테스트가 깨집니다

가장 자연스러워 보이는 선택 — `from_env()` 첫 줄에 `load_dotenv()`를 넣는 것 — 은 함정이 있습니다. [test_config.py:27](pipelines/tests/test_config.py#L27)의 `test_from_env_missing_oc_raises`가 `LAW_API_OC`를 지우고 `RuntimeError`를 기대하는데, `.env`가 존재하는 개발자 머신에서는 값이 되살아나 **테스트가 실패**합니다. `.env`가 없는 CI에서는 통과하니 재현도 까다롭습니다.

그래서 위 설계는 로딩을 **`main()`(CLI 경계)에 두고 `from_env()`는 순수하게** 남겼습니다. `from_env()`는 "환경변수를 읽는 함수"로 유지되고, ".env 파일을 찾아 읽는" 것은 CLI의 편의 기능이라는 역할 분리이기도 합니다. 기존 테스트 4개는 수정 없이 그대로 통과합니다.

## 정리

| | 방법 1 (`--env-file`) | 방법 2 (모듈 내 로드) |
|---|---|---|
| 코드 변경 | 없음 | pyproject 1줄 + config 12줄 + main 4곳 |
| 새 의존성 | 없음 | `python-dotenv` |
| `uv run` 없이도 동작 | ✗ | ✓ |
| 실수로 빠뜨릴 여지 | 있음 | 없음 |

지금 당장 돌려보는 게 목적이면 **방법 1**, 팀이 쓸 공개 CLI로 굳힐 거라면 **방법 2**입니다.

방법 2로 구현해드릴까요? 앞서 미뤄둔 `[project.scripts]` 등록과 한 번에 처리하는 게 효율적입니다 — 명령 형태(개별 4개 vs 통합 서브커맨드)만 정해주시면 `.env` 로딩까지 묶어서 작업하고 테스트로 검증하겠습니다.
