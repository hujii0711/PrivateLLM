`eval`·`finetune` 의존까지 확인했습니다. 이제 전체 워크스페이스의 **코드 의존(import)**과 **데이터 흐름(파일 산출물)**을 하나로 통합한 다이어그램을 작성합니다.

## 1. 코드 의존 DAG (import만, 비순환)

```
pipelines        ← (누구도 import 안 함; 데이터로만 연결)
rag              ← api, eval, ftdata
api   → rag      ← eval, ftdata, finetune
eval  → rag, api ← ftdata, finetune
ftdata→ rag, api, eval
finetune→ api, eval
```

위상 정렬(아래→위로 의존):

| 레이어 | 패키지 | 워크스페이스 의존 | 성격 |
|---|---|---|---|
| L0 | **pipelines** | (없음) | ETL·write, 완전 독립 |
| L0 | **rag** | (없음) | 검색·프롬프트 코어, read |
| L1 | **api** | rag | 서빙(FastAPI/SSE) |
| L2 | **eval** | rag, api | 평가 하니스 |
| L3 | **ftdata** | rag, api, eval | 학습데이터 빌더 |
| L3 | **finetune** | api, eval | QLoRA 학습·A/B |

→ **pipelines·rag가 두 뿌리**, api가 허브, eval이 그 위, ftdata·finetune이 최상위 소비자. 순환 없음.

## 2. 데이터 흐름 DAG (파일 산출물, 코드와 별개)

```
DRF API ─▶ data/raw/*.json ─▶ data/chunks/chunks.jsonl ─▶ data/chroma ─┐
                                                  (pipelines)           │
                                                                        ├─▶ [api] 서빙 응답(SSE)
   eval_set.jsonl(repo) ──────────────────────────────────────────────┤
                                                                        ├─▶ [eval] 측정 → 결과
   question_pool.jsonl(repo) ─▶ [ftdata] run_chat+judge+filter ─▶ data/ft/{train,valid}.jsonl
                                                                        │
   data/ft ─▶ [finetune] mlx_lm.lora ─▶ data/adapters ─▶ [api]MlxLLM(adapter_path) / [eval]--adapter
                                                                        └─▶ notes/ab-result.md
```

핵심: **코드는 import로, 단계는 파일로** 연결됩니다. 특히 `pipelines→rag`는 **import가 전혀 없고** 오직 `data/chroma`(+상수 계약)로만 이어집니다.

## 3. 횡단 계약·재사용 (다이어그램이 숨기는 결합)

| 종류 | 내용 | 묶는 대상 |
|---|---|---|
| **상수 계약** | `COLLECTION="jeonse_deposit"`·`MODEL_NAME="BAAI/bge-m3"`·cosine | pipelines(write) ↔ rag(read) — 중복 정의, 일치 필수 |
| **경로 계약** | `data/{raw,chunks,chroma,ft,adapters}` | 모든 배치 단계 |
| **`run_chat` 재사용** | 서빙 경로를 eval(측정)·ftdata(후보생성)가 그대로 호출 | "서빙=평가=학습 입력" 일치 |
| **`answer_metrics`/`judge` 재사용** | eval 지표를 ftdata 필터가 재사용 | "선별기준=평가기준" |
| **`build_messages` 재사용** | rag 프롬프트를 ftdata builder가 학습입력에 재사용 | "train입력=서빙입력" |
| **`LLM` Protocol** | MlxLLM/FakeLLM/(OpenAICompat) 교체점 | 배포 3환경 단일 코드베이스 |
| **train/eval 오염 금지** | `question_pool`(30) ∩ `eval_set`(16) = ∅ | ftdata ↔ eval (held-out 보장) |

## 4. 한눈에 보는 역할·산출물 표

| 패키지 | 입력 | 처리 | 산출물 | 진입점 |
|---|---|---|---|---|
| pipelines | DRF API | 수집→정규화→구조청킹→임베딩 | **data/chroma** | 3개 `-m`(fetch/chunk/build_index) |
| rag | 질의, data/chroma | 검색·근거판정·프롬프트·인용 | (라이브러리) | — |
| api | 사용자 메시지 | run_chat 오케스트레이션 | SSE 응답 | `uvicorn api.main:app` |
| eval | eval_set.jsonl | run_chat 측정·judge | 평가 리포트 | `-m eval.cli` |
| ftdata | question_pool.jsonl | rejection-sampling distillation | **data/ft** | `-m ftdata.cli` |
| finetune | data/ft | mlx_lm.lora·A/B | **data/adapters**, ab-result | `-m finetune.compare_cli` 등 |
