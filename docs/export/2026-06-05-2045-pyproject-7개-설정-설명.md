7개 서브에이전트의 분석을 종합합니다. 먼저 공통 패턴을 한 번 정리하고, 파일별 고유 설정을 설명합니다.

## 0. 전체 개요 — 7개 파일의 역할

| 파일 | 패키지 성격 | 워크스페이스 의존 | 외부 런타임 의존 | 빌드 대상 |
|---|---|---|---|---|
| **루트** `pyproject.toml` | 워크스페이스 허브(패키지 아님) | — (멤버 정의자) | — | 없음(`[project]` 없음) |
| `pipelines` | ETL·색인(write, 독립) | **없음** | requests·lxml·chromadb·sentence-transformers | src/pipelines |
| `packages/rag` | 검색·프롬프트 코어(read, 뿌리) | **없음** | chromadb·sentence-transformers | src/rag |
| `apps/api` | FastAPI 서빙 | rag | fastapi·uvicorn·sse-starlette·pydantic·mlx-lm | src/api |
| `packages/eval` | 평가 하니스 | rag·api | (없음, 워크스페이스만) | src/eval |
| `packages/ftdata` | 학습데이터 빌더(최상위 소비자) | rag·api·eval | (없음) | src/ftdata |
| `packages/finetune` | QLoRA 학습·A/B | api·eval | (없음, mlx_lm은 커맨드로 호출) | src/finetune |

→ 의존 방향이 **rag/pipelines(뿌리) → api → eval → ftdata/finetune**으로 흐르며 순환이 없습니다. 의존 선언이 곧 §통합 다이어그램의 화살표입니다.

## 1. 6개 멤버 패키지의 공통 패턴 (루트 제외)

6개 멤버는 동일한 골격을 공유합니다(아래는 한 번만 설명, 파일별로 반복 안 함):

- **`[project]`**: `version="0.1.0"`(PoC), `requires-python=">=3.11"`(워크스페이스 공통 런타임 고정), 한국어 `description`.
- **`[dependency-groups]` `dev = ["pytest>=8.0"]`**: 테스트 전용. 런타임 배포물에서 분리.
- **`[tool.pytest.ini_options]`**: `pythonpath=["src"]`(src 레이아웃이라 설치 없이 import), `testpaths=["tests"]`(수집 범위 한정), `markers=["slow: ..."]`(무거운 통합 테스트 분리 + 미등록 마커 경고 방지).
- **`[build-system]`**: `requires=["hatchling"]` + `build-backend="hatchling.build"`(PEP 517 표준, 가벼움).
- **`[tool.hatch.build.targets.wheel]` `packages=["src/<name>"]`**: src 레이아웃에서 hatchling이 담을 패키지 디렉터리 명시.
- **`[tool.uv.sources]`**: 워크스페이스 의존을 `{ workspace = true }`로 — PyPI가 아닌 모노레포 로컬 소스로 해석(로컬 코드 변경 즉시 반영). *단 워크스페이스 의존이 없는 `rag`·`pipelines`에는 이 섹션이 없음.*

`slow` 마커 문구만 패키지별로 다릅니다: api `"실제 MLX 모델"`, rag/eval/ftdata `"실제 모델/인덱스"`, finetune `"실제 모델/학습"`, pipelines `"실제 모델/네트워크"` — 각 패키지에서 "느린 것"의 정체를 그대로 반영합니다.

## 2. 파일별 고유 설정

### 루트 `pyproject.toml` — 워크스페이스 허브 + Ruff
`[project]`가 **없습니다**(배포 패키지 아님). 두 가지만 정의:
- **`[tool.uv.workspace]`**: `members=["pipelines","packages/*","apps/*"]`로 멤버를 글롭 편입, `exclude=["apps/web"]`로 Next.js 앱을 uv 해석에서 제외(Python 멤버 오인 방지).
- **`[tool.ruff]`** (앞서 추가): `target-version="py311"`, `line-length=100`, `extend-exclude=[".venv","data","models","apps/web","**/__pycache__"]`(생성물·대용량 제외). `[tool.ruff.lint] select=["E","W","F","I","UP","B"]`(스타일+pyflakes+isort+pyupgrade+bugbear). `[tool.ruff.lint.isort] known-first-party=["rag","api","pipelines","eval","ftdata","finetune"]`로 내부 패키지를 import 정렬에서 별도 그룹화.

### `pipelines` — 완전 독립 ETL
런타임 의존 4개가 **ETL 단계와 1:1**: `requests`(법령 API 수집) → `lxml`(XML 파싱) → `sentence-transformers`(bge-m3 임베딩) → `chromadb`(색인). **워크스페이스 의존·`[tool.uv.sources]` 없음** → rag와는 코드가 아닌 산출물(`data/chroma`)로만 연결.

### `packages/rag` — 뿌리 라이브러리
런타임 의존은 `chromadb>=0.5`·`sentence-transformers>=3.0` **둘뿐**, **워크스페이스 의존 없음**(`[tool.uv.sources]` 부재) → 다른 사내 패키지에 안 기대는 read-path 코어임이 설정으로 확인됨.

### `apps/api` — 유일하게 외부 런타임 의존이 풍부
`fastapi>=0.115`·`uvicorn[standard]>=0.30`(uvloop/httptools 포함)·`sse-starlette>=2.1`(토큰 스트리밍)·`pydantic>=2.7`·`mlx-lm>=0.18`(MLX 추론) + 워크스페이스 `rag`. **dev에 `httpx>=0.27` 추가**(FastAPI TestClient/HTTP 테스트용) — 6개 중 dev가 pytest 외 항목을 가진 유일한 패키지. `[tool.uv.sources] rag={workspace=true}`.

### `packages/eval` — 서빙=평가 동일성의 근거
런타임 의존 `rag`·`api`(둘 다 workspace). **`api` 의존이 핵심**: 평가 러너가 `api.pipeline.run_chat`을 그대로 재사용 → 별도 추론 코드 없이 "실서빙 경로 = 평가 경로" 보장.

### `packages/ftdata` — 최상위 소비자 (rag+api+eval)
세 패키지 모두 workspace 의존. 각 의존이 재사용 지점과 대응: `rag`→`build_messages`(학습입력=서빙입력), `api`→`run_chat`(후보 생성), `eval`→`answer_metrics`(선별기준=평가기준). 의존 선언이 곧 "일관성 강제" 설계의 표현.

### `packages/finetune` — 학습·A/B
런타임 의존 `api`·`eval`(workspace). `api`→어댑터 적용(`MlxLLM(adapter_path=)`)·추론, `eval`→A/B 측정. **학습 자체(`mlx_lm.lora`)는 커맨드 빌더로 외부 호출**하므로 학습 프레임워크가 의존성에 안 나타남 — 의존성에 mlx-lm이 없는 이유.

## 3. 한눈에 보는 결론

- **의존 그래프는 설정에 그대로 박혀 있다**: `dependencies` + `[tool.uv.sources]`가 워크스페이스 DAG(뿌리 rag/pipelines → api → eval → ftdata/finetune)를 정의.
- **모든 멤버가 동일 골격**(src 레이아웃·hatchling·pytest·slow 마커·dev 분리)이라 일관성·온보딩이 좋음.
- **외부 런타임 의존은 책임에 비례**: 무거운 건 pipelines(수집·임베딩)·api(웹·MLX)·rag(검색)뿐이고, eval·ftdata·finetune은 **워크스페이스 재사용만**으로 동작 → 중복 코드 없이 상위 기능을 조립.

이제 이 설명을 export-last-response 스킬로 문서화하겠습니다.
