둘 다 쓰되 **용도를 나누는 것**이 정답입니다. 그리고 사실 둘은 배타적이지 않습니다 — `uv run pipelines-ingest`로 합칠 수 있습니다.

## 핵심 차이

| | `uv run python -m ...` | 콘솔 스크립트 |
|---|---|---|
| 사전 준비 | 없음 (uv가 실행 전 자동 동기화) | `uv sync`로 설치 필요 |
| 이름 | 내부 모듈 경로가 그대로 노출 | 안정적인 공개 이름 |
| 리팩터링 내성 | 모듈 이동 시 문서·스크립트 전부 깨짐 | 진입점만 고치면 됨 |
| 발견 가능성 | 코드를 뒤져야 알 수 있음 | `ls .venv\Scripts\`, `--help` |
| 환경 보장 | uv가 항상 최신 의존성 보장 | 활성화한 venv에 의존 |

## 결론

**공개 CLI에는 콘솔 스크립트가 맞습니다.** `python -m pipelines.ingest.fetch_corpus`는 *구현 세부사항*을 인터페이스로 노출하는 형태입니다. 지금 `fetch_corpus.py`를 다른 모듈로 옮기거나 이름을 바꾸면 [LLM_ARCHITECTURE.md:164](docs/LLM_ARCHITECTURE.md#L164), [pipelines/README.md:13-16](pipelines/README.md#L13-L16), 그리고 사용자가 적어둔 스크립트가 전부 깨집니다. 콘솔 스크립트는 그 사이에 한 겹을 두어 `pyproject.toml` 한 줄만 고치면 끝나게 만듭니다. 애초에 "공개 CLI를 만들라"는 요구가 바로 이 문제를 푸는 것입니다.

**다만 `uv run` 접두사는 유지하세요:**

```powershell
uv run pipelines-ingest
uv run pipelines-chunk
uv run pipelines-index
uv run pipelines-query "보증금을 못 받았어요"
```

이 형태가 양쪽 장점을 다 가집니다 — uv가 실행 전에 환경을 동기화해주므로 venv 활성화도, 의존성이 낡았는지 걱정할 필요도 없고, 이름은 짧고 안정적입니다. 문서에 적기에 가장 좋은 형태입니다.

## 예외 — `-m`이 더 나은 경우

- **디버깅·개발 중**: 콘솔 스크립트는 `[project.scripts]`를 고칠 때마다 `uv sync`가 필요합니다. 진입점 자체를 실험 중이라면 `-m`이 그 왕복을 건너뜁니다.
- **아직 설치되지 않은 상태에서의 일회성 실행**.
- **교육용 문서**: 코드가 실제로 어디 있는지 보여주는 게 목적이라면 모듈 경로가 오히려 정보입니다. [LLM_ARCHITECTURE.md](docs/LLM_ARCHITECTURE.md)가 아키텍처 설명 문서라면 `-m` 표기를 남겨두는 것도 합리적입니다.

## 사소한 주의점

`-m`은 모듈을 `__main__`으로 로드하고, 콘솔 스크립트는 모듈을 정상 import한 뒤 `main()`을 호출합니다. 지금 네 모듈은 `if __name__ == "__main__": main()` 형태가 동일해서 실동작 차이는 없습니다. 다만 `-m`으로 실행한 모듈을 다른 곳에서 import하면 같은 모듈이 두 번 적재되어 전역 상태가 분리되는 함정이 있습니다 — 콘솔 스크립트에는 없는 문제입니다.
