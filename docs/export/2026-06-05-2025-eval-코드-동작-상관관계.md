`packages/eval`는 보증금 반환 챗봇의 **RAG 품질 평가 하네스**입니다. 8개 파일이 명확히 계층 분리돼 있고, 의존 방향이 한쪽으로만 흐릅니다. 전체 구조와 파일 간 상관관계를 정리합니다.

## 전체 데이터 흐름

```
eval_set.jsonl
   │  dataset.load_eval_set()
   ▼
[EvalItem] ──────────────────────────────► cli.main() (오케스트레이터)
                                               │  항목별 반복
                                               ▼
                                          runner.run_item()
                            ┌──────────────────┼─────────────────────┐
                            ▼                  ▼                     ▼
                     retriever.retrieve   api.pipeline.run_chat   judge_fn(LLM)
                            │                  │                     │
                            ▼                  ▼                     ▼
              retrieval_metrics.ref_hit  answer_metrics()   judge.groundedness_score
                            └──────────────────┼─────────────────────┘
                                               ▼
                                          [ItemResult]
                                               │  report.aggregate()
                                               ▼
                                     data/eval_runs/<label>.json
```

## 계층별 역할

**1. 데이터 계층 — [dataset.py](packages/eval/src/eval/dataset.py)**
- `EvalItem` 데이터클래스 + `eval_set.jsonl` 로더. 평가셋의 스키마를 정의합니다.
- 항목 하나 = `question`(질문) + `expected_refs`(기대 법조항) + `must_mention`(필수 키워드).
- 이 두 필드가 각각 **검색 평가**와 **답변 평가**의 정답지(ground truth) 역할을 합니다.

**2. 지표 계산 계층 (순수 함수, 외부 의존 없음)**
세 파일 모두 입력만 받아 결정적으로 점수를 내는 stateless 함수라 단위 테스트가 쉽습니다.

- [retrieval_metrics.py](packages/eval/src/eval/retrieval_metrics.py) — **검색 품질**. `ref_hit()`은 기대 법조항이 top-k 검색결과에 하나라도 있으면 hit. `expected_refs`가 비면 평가 제외(True 반환)하는 게 포인트. `recall_at_k()`는 hit 불리언 리스트의 평균.
- [answer_metrics.py](packages/eval/src/eval/answer_metrics.py) — **답변 형식·키워드 준수**(LLM 없이 정규식/문자열로 결정적 판정). 인용 `[1]` 존재, 구조 마커 `①②③`, 면책문구, 출처 유무, `must_mention` 키워드 커버리지를 딕셔너리로 반환.
- [judge.py](packages/eval/src/eval/judge.py) — **groundedness**(근거 기반성). 유일하게 LLM을 쓰는 지표. `build_judge_prompt()`로 질문/근거/답변 프롬프트를 만들고, 주입된 `judge_fn`을 호출해 나온 텍스트에서 첫 숫자를 뽑아 0~1로 클램프. `judge_fn`을 **주입**받는 설계라 테스트 시 가짜 함수로 교체 가능.

**3. 실행 계층 — [runner.py](packages/eval/src/eval/runner.py)**
- 지표 계층 3개를 한 항목에 대해 묶어 실행하는 **조합기**. 위 2계층에 의존(import)하지만 역방향 의존은 없습니다.
- `run_item()` 한 번에서: ① `retriever.retrieve()`로 검색 → `ref_hit` ② `api.pipeline.run_chat`을 스트리밍 이벤트로 소비해 `done` 이벤트에서 최종 `answer`/`sources` 추출 → `answer_metrics` ③ 검색된 문맥 텍스트로 `groundedness_score`.
- 결과를 `ItemResult` 데이터클래스로 반환. **여기서 처음으로 외부 패키지(`api`)에 의존**합니다.

**4. 집계 계층 — [report.py](packages/eval/src/eval/report.py)**
- `ItemResult` 리스트 → 지표별 평균 딕셔너리(`aggregate`). `runner.ItemResult`만 의존하는 얇은 계층. 빈 결과는 `{"n": 0}`로 방어.

**5. 오케스트레이션/진입점 — [cli.py](packages/eval/src/eval/cli.py)**
- 실제 운영 객체를 조립해 전체를 돌리는 유일한 진입점(`uv run --package eval python -m eval.cli`). 위 모든 계층을 import하는 최상위.
- `Settings.from_env()` → `Retriever`, `MlxLLM` 생성 → 평가셋 로드 → 항목별 `run_item` 반복 → `aggregate` → `data/eval_runs/<label>.json` 저장.
- 주목할 설계 포인트:
  - `--adapter`로 파인튜닝 어댑터 arm 평가 지원.
  - **judge LLM은 항상 base 모델로 고정**(cli.py:33-34) — 생성은 어댑터, 채점은 base로 분리해 A/B 공정성 확보. 어댑터 없으면 같은 인스턴스 재사용으로 메모리 절약.
  - judge는 `temperature=0.0, max_tokens=16`(cli.py:36) — 결정적이고 숫자만 뽑으면 되므로.

## 의존 방향 요약

```
cli → runner → {dataset, answer_metrics, judge, retrieval_metrics} + 외부(api, rag)
cli → report → runner
지표 3종 → (의존 없음, 순수 함수)
```

핵심 설계 의도는 **결정적 지표(형식/검색)와 비결정적 지표(LLM judge)를 분리**하고, judge_fn·retriever·llm을 모두 **주입(injection)**으로 받아 러너를 외부 의존에서 떼어낸 것입니다. 덕분에 지표 계층은 LLM 없이 단위 테스트가 가능하고, cli만 실제 인프라를 조립합니다. `--label`/`--adapter` 조합으로 baseline vs 어댑터 결과를 각각 JSON으로 떨궈 A/B 비교하는 워크플로우입니다.
