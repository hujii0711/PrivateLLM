`packages/finetune`는 보증금 챗봇의 **QLoRA 파인튜닝 + A/B 비교 도구**입니다. eval 패키지와 짝을 이루는데, eval이 "측정"을 담당한다면 finetune은 "학습 명령 생성"과 "두 측정 결과의 비교"를 담당합니다. 파일은 3개(+빈 `__init__.py`)로 매우 작고, 두 갈래로 나뉩니다.

## 두 개의 독립 갈래

```
[갈래 A: 학습]                          [갈래 B: A/B 비교]
train.py                               compare.py  ← compare_cli.py
build_lora_command()                   load_summary/compare_runs/to_markdown
   │                                       │
   │ list[str] 반환                        │ data/eval_runs/{baseline,qlora}.json 읽음
   ▼                                       ▼
호출 측이 subprocess 실행                  지표별 델타 + 마크다운 표 출력
(mlx_lm.lora 학습)
```

두 갈래는 서로 import하지 않습니다. 연결고리는 **코드가 아니라 파일/워크플로우**입니다 — train이 만든 어댑터로 eval을 두 번 돌려(`baseline.json`, `qlora.json`) 나온 결과를 compare가 읽습니다.

## 파일별 역할

**1. [train.py](packages/finetune/src/finetune/train.py) — 학습 명령 빌더**
- `build_lora_command()` 단 하나의 순수 함수. `mlx_lm.lora` CLI 명령을 `list[str]`로 **조립만** 하고, **실제 실행은 하지 않습니다**(독스트링: "라이브 실행은 호출 측에서 subprocess").
- 이 분리가 핵심 설계 의도입니다. 명령 조립 = 결정적·테스트 가능, subprocess = 부수효과·느림. 둘을 떼어내 [test_train.py](packages/finetune/tests/test_train.py)가 GPU 없이 명령 문자열만 검증할 수 있습니다.
- 하이퍼파라미터는 소규모 학습셋(~45개) 기준 보수값을 기본 인자로: `iters=300, batch_size=1, num_layers=8, learning_rate=1e-5`. mlx-lm 0.31.3 인터페이스에 고정.
- 학습 데이터는 ftdata 패키지가 만든 `data/ft/{train,valid}.jsonl`을 `--data`로 받습니다(이 패키지 밖 산출물).

**2. [compare.py](packages/finetune/src/finetune/compare.py) — A/B 비교 로직 (순수 함수 3종)**
- `load_summary(path)` — eval이 떨군 run JSON에서 `["summary"]` 블록만 추출. **eval의 `report.aggregate()` 출력 스키마에 의존**합니다(`_METRICS` 리스트가 eval의 집계 키와 일치해야 함).
- `compare_runs(baseline, qlora)` — 7개 지표 각각에 대해 `{baseline, qlora, delta}` 딕셔너리 생성. 양쪽 모두에 있는 지표만 비교(방어적).
- `to_markdown(comparison)` — 결과를 `| 지표 | baseline | qlora | Δ |` 마크다운 표로. `delta`는 `+.3f`로 부호 표시.
- 외부 의존이 전혀 없어(`json`/`pathlib`만) [test_compare.py](packages/finetune/tests/test_compare.py)로 단위 테스트 가능.

**3. [compare_cli.py](packages/finetune/src/finetune/compare_cli.py) — A/B 진입점**
- `data/eval_runs/baseline.json`과 `qlora.json`을 읽어 `compare.py` 3함수를 엮고 표를 stdout으로 출력. 실행: `uv run --package finetune python -m finetune.compare_cli`.
- compare.py에만 의존하는 얇은 오케스트레이터.

## eval 패키지와의 관계 (전체 워크플로우)

이 두 패키지는 `data/eval_runs/` 디렉터리를 매개로 파이프라인을 이룹니다:

```
1. finetune.train.build_lora_command  → (subprocess) → 어댑터 생성
2. eval.cli                            → baseline.json  (어댑터 없이)
3. eval.cli --adapter <path>           → qlora.json     (어댑터 적용)
4. finetune.compare_cli                → baseline.json vs qlora.json 비교 표
```

이전에 분석한 eval.cli의 설계와 정확히 맞물립니다 — eval은 `--adapter` 인자로 두 arm을 같은 코드·같은 judge(base 모델 고정)로 측정해 공정성을 확보하고, finetune.compare는 그 산출물의 **델타만 계산**합니다. A/B의 주 신호는 결정적 지표(structure/citation/disclaimer 등)이고, 검색은 양 arm 동일이라 `recall_at_k`는 불변이어야 한다는 게 검증 포인트입니다.

## 설계 패턴 요약

eval과 동일한 철학이 관통합니다: **"순수 함수(테스트 가능) + 얇은 CLI(조립·부수효과)"** 분리. train.py는 subprocess를 분리하고, compare.py는 파일 I/O를 compare_cli로 밀어냈습니다. 덕분에 핵심 로직 전부가 GPU·실제 모델 없이 단위 테스트되며, 무거운 실행(학습·평가)만 CLI/수동 단계에 남습니다.
