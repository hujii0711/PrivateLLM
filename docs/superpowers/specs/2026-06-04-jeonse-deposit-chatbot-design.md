# 로컬 LLM 기반 주택임대차 보증금 반환 상담 챗봇 — 설계 문서

- **작성일:** 2026-06-04
- **상태:** 승인됨 (구현 계획 작성 대기)
- **목적:** 학습·연구용 PoC

---

## 1. 개요

로컬 LLM(Apple Silicon, MLX)을 기반으로 **주택임대차 보증금 반환** 민사 문제에 대해
**상담형 + 근거·출처 명시** 답변을 제공하는 챗봇을 구축한다.
**RAG**(검색 기반 지식 주입)와 **QLoRA 파인튜닝**(상담형 말투·인용 형식 학습)을 혼용하되,
연구 목적에 맞게 **RAG 베이스라인을 먼저 완성한 뒤 QLoRA를 추가해 A/B로 기여도를 측정**한다.

### 1.1 목표 (Success Criteria)
1. 보증금 반환 질문에 대해 검색된 법령·판례를 근거로 한 상담형 답변을 생성한다.
2. 답변에 `[n]` 형식 인용을 달고, 인용번호를 실제 출처(법조항/판례/해설)로 매핑해 UI에 표시한다.
3. RAG-only 베이스라인과 RAG+QLoRA를 동일 평가셋으로 비교해 파인튜닝의 정량적 기여도를 산출한다.

### 1.2 비범위 (Out of Scope)
- 주택임대차 보증금 반환 **외** 민사 주제 (도메인 가드로 차단).
- 상용 서비스 수준의 법적 면책·보안. (학습·연구용 고지로 대체)
- 문서(내용증명·지급명령신청서) 자동 작성. (향후 확장 여지로만 남김)

## 5. 데이터 파이프라인 & RAG

### 5.1 데이터 소스 (주택임대차·보증금 반환 특화)

| 소스 | 용도 | 수집 방식 |
|---|---|---|
| 국가법령정보센터 OPEN API (open.law.go.kr) | 법령 원문 — 주택임대차보호법, 민법 임대차편(618~654조) | 무료 API 키, 조문 단위 |
| 찾기쉬운 생활법령정보 (easylaw.go.kr) | 생활법령 Q&A·해설 (쉬운 말) | 크롤링/API |
| 대법원 판례 (law.go.kr 판례 API) | 보증금 반환 관련 판례 (판시사항·판결요지) | API |
| 대한법률구조공단 (klac.or.kr) | 상담사례·법률서식 | 크롤링 |

### 5.2 파이프라인 단계 (`pipelines/ingest` → `index`)

1. **수집** — 소스별 fetcher가 원시 데이터를 `data/raw/`에 JSON 저장 (출처 URL·날짜 메타 포함).
2. **정제** — HTML 제거, 조문/판례 구조 파싱, 중복 제거 → `data/clean/`.
3. **청킹** — 구조 인지 청킹: 법령=조문 단위, 판례=판시사항/판결요지 단위, 해설=단락 단위.
4. **임베딩·색인** — bge-m3로 임베딩 → Chroma에 저장.

### 5.3 청크 메타데이터 스키마

```json
{
  "id": "...", "text": "...",
  "source_type": "법령|판례|해설|상담사례",
  "title": "주택임대차보호법 제3조의2",
  "ref": "조문번호 또는 사건번호",
  "url": "https://...", "date": "2023-..."
}
```

### 5.4 RAG 질의 흐름 (`packages/rag`)

```
질문 → bge-m3 임베딩 → Chroma top-k 검색(k≈6)
     → (2단계)리랭크 → 번호 매긴 근거로 프롬프트 조립
     → Qwen 생성([1][2] 형식 인용) → 인용번호를 출처 메타로 매핑
     → {answer, sources[]} 반환 → UI가 답변+출처 카드 렌더
```

## 6. QLoRA 파인튜닝

**목표: 지식 주입이 아니라 행동 학습** — 상담형 어조, 구조화된 답변(상황 요약 → 적용 법리 → 다음 절차), `[n]` 인용 포맷 준수.

### 6.1 학습 데이터셋 (`pipelines/finetune`)

- 소스: 생활법령 Q&A + 대한법률구조공단 상담사례 (수집 코퍼스 재활용).
- 변환: 원시 상담사례 → "근거 인용이 달린 상담형 정답" 형태로 합성(distillation) 후 사람이 샘플 검수.
- 규모: **약 500~1,500쌍** (형식 학습은 품질 > 양).
- 포맷: MLX chat JSONL — `{"messages":[{"role":"user",...},{"role":"assistant","...(근거·출처 포함)"}]}`,
  `train.jsonl` / `valid.jsonl` 분리.

### 6.2 학습 절차 (`mlx_lm.lora`)

```
1) mlx_lm.convert --hf-path Qwen/Qwen2.5-7B-Instruct -q       # 4bit 양자화
2) mlx_lm.lora --train --data ./data/ft \
     --iters ~1000 --batch-size 2 --lora-layers 16 --learning-rate 1e-5
3) (선택) mlx_lm.fuse                                          # 어댑터 융합 또는 런타임 로드
```

- 48GB 통합 메모리면 7B 4bit QLoRA는 여유롭다. (하이퍼파라미터는 검증 단계에서 튜닝)
- 산출물: `models/adapters/` 의 LoRA 어댑터 → FastAPI가 베이스+어댑터로 서빙.

## 7. 평가 (단계적 전략의 핵심)

### 7.1 지표

| 차원 | 지표 | 방법 |
|---|---|---|
| 검색 품질 | recall@k / hit@k | 평가셋의 정답 법조항·판례가 검색됐는가 |
| 답변 충실도 | groundedness/faithfulness | LLM-as-judge: 답변이 검색 근거에 실제 기반했는가 |
| 인용 정확도 | citation accuracy | `[n]`이 주장을 실제 뒷받침하는가, 환각 인용률 |
| 말투·구조 | 적합성 점수 | 상담형 형식 준수도 (judge) |

### 7.2 방법

- **평가셋:** 보증금 반환 대표 질문 **30~50개** + 기대 출처/참고답안을 수작업 구축 (`data/eval/`).
- **A/B 비교:** `① RAG만(베이스라인)` vs `② RAG+QLoRA` 를 **동일 평가셋·동일 검색 결과**로 돌려 점수 델타 측정.
- 검색이 두 조건에서 동일하므로 차이는 "생성·형식" 측면의 FT 효과로 해석한다.

## 8. 에러 처리 & 견고성

| 상황 | 처리 |
|---|---|
| 검색 결과 부적합 / 빈 결과 (점수 임계치 미달) | 추측 답변 금지 → "근거를 찾지 못했습니다" + 재질문 유도 |
| 범위 밖 질문 (보증금 반환 외) | 도메인 가드: 범위 벗어남 안내 + 다루는 주제 명시 |
| LLM 생성 실패 / 타임아웃 | FastAPI 에러 코드 반환, UI 재시도 버튼 |
| 외부 데이터 API 장애 (수집 시) | fetcher 재시도·백오프, 부분 실패 로깅, 받은 데이터로 진행 |
| 환각 인용 (`[n]`이 근거에 없음) | 백엔드에서 인용번호 검증, 존재하지 않는 인용 제거/플래그 |
| 면책 | 학습·연구용임을 답변 하단에 고정 고지 (법률 자문 아님) |

## 9. 테스트 (TDD 기조)

- `packages/rag` — 청킹·프롬프트 조립·인용 매핑 **단위 테스트** (순수 로직 우선).
- 검색 — 골든셋으로 recall@k **회귀 테스트**.
- FastAPI — `/chat` 엔드포인트 **통합 테스트** (LLM은 목/소형 모델로 대체).
- 파이프라인 — 정제·청킹 스키마 검증 테스트 (메타데이터 필수 필드).
- 평가 스크립트 자체가 시스템 품질의 지속 측정 역할.

## 10. 구현 순서

각 단계가 독립적으로 검증 가능하도록 구성한다.

```
0. 모노레포 스캐폴딩 (apps/web, apps/api, pipelines, packages/rag)
1. 데이터 수집 파이프라인 → data/raw, data/clean          ← 모든 것의 전제
2. 청킹 + bge-m3 임베딩 + Chroma 색인
3. packages/rag (검색·프롬프트 조립·인용 매핑) + 단위테스트
4. FastAPI /chat (RAG + Qwen2.5 MLX 서빙)              ── ★베이스라인 완성★
5. Next.js 채팅 UI (스트리밍 + 출처 카드)
6. 평가셋 구축 + 평가 스크립트 → 베이스라인 점수 측정
7. FT 데이터셋 빌더 + QLoRA 학습(mlx_lm.lora) → 어댑터
8. 어댑터 서빙 적용 + A/B 평가 → 파인튜닝 기여도 측정
```

- **4단계:** 데모 가능한 RAG 챗봇 완성.
- **8단계:** 연구 결론(파인튜닝 효과) 산출.
